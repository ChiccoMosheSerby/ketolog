01 · Overview

What this is

Log meals in free-text Hebrew, photograph a product label, or scan a barcode — the app turns any of them into net carbs / fat / protein and keeps a per-user cloud diary with daily metrics, saved products, a tool-using keto chat assistant, and periodic insights.

Three design commitments shape everything below:

  • One origin. The browser only ever talks to the Express server. In production Express also serves client/dist, so there is no CORS story and the Anthropic key never leaves the server.
  • Local before AI. Every meal description first tries a deterministic match against the user's own saved products (mealResolver), then a cache (estimateCache), and only then a paid Claude call. The resolver's rule is precision over recall: any doubt falls through to the AI rather than risk a silently wrong number in the log.
  • The AI proposes, the user commits. The chat assistant's write tools never touch the database; they emit confirmation cards, and the browser commits them through the ordinary REST routes only after a tap.
02 · System map

One process, five neighbors

Everything funnels through the Express app in server/src/index.js. External services hang off the right edge; two of them are wired but currently switched off in code.

Why one origin matters here

The CORS layer is an allowlist that withholds headers instead of throwing on unknown origins — because the approval / password-reset forms arrive via cross-origin email-link redirects that send an unrecognized (often null) Origin and must still work. Same-origin deployment makes CORS a non-event for the app itself.

03 · Request flow

Anatomy of a meal estimate

POST /api/ai/estimate-meal is the most layered request in the app — it crosses every middleware, two money-saving short-circuits, and finally Claude. Each right-hand exit is an early response; only the bottom path costs anything.

The other flows, briefly

  • Photo → product: POST /api/ai/estimate-image sends a base64 label photo (hence the 12 MB JSON body limit) straight to Claude vision with the same keto rules; the result pre-fills a confirm/edit form, never the log directly.
  • Barcode: POST /api/ai/barcode asks Open Food Facts for raw nutrition, then Claude converts it to keto net carbs. Unknown barcode → 404 {found:false} and the UI falls back to the photo flow.
  • Chat: POST /api/ai/chat runs a tool-use loop (max 6 turns). Read tools query MongoDB scoped to the user; write tools only propose — the browser commits accepted cards via /api/days and /api/products.

07 · The AI layer

One rulebook, many mouths

shared/ketoCore.js is the single source of truth for how net carbs are computed — fiber and which sugar alcohols to subtract, Israeli/EU vs US label conventions, a mass-balance sanity check for non-compliant labels. It is imported verbatim by both sides:

  • Server — lib/anthropic.js builds the estimator system prompts (meal / image / barcode) from it.
  • Client — lib/ketoPromptRules.js embeds it in a claude.ai/new?q=… deep link (the ClaudeCalcModal flow), so a user calculating in the Claude app gets the same rules. It's kept compact because percent-encoded Hebrew inflates ~6× in a URL.

Who pays for tokens

lib/aiAccess.js resolves a key per request: owner accounts ride the app's ANTHROPIC_API_KEY; everyone else brings their own key, stored encrypted, with invalid-key / out-of-credit errors flagged on the user and explained specifically (402) rather than as a generic failure. Per-user usage is metered and a monthly budget can be set. Estimators and chat each pin their model via CLAUDE_MODEL / CHAT_MODEL (both default claude-opus-4-8), and the SDK runs with maxRetries: 4 so brief API overloads self-heal mid-chat.

The chat assistant (lib/chatAgent.js) is a proper tool-using agent with a hard 6-turn loop cap: read tools (get_today_log, get_log, get_recent_days, list_products) hit MongoDB live, write tools (propose_meal, propose_product) only ever surface confirmation cards.

08 · Run & deploy

Local in two terminals, prod in one service

Local

# once: server/.env from server/.env.example
#   MONGODB_URI, ANTHROPIC_API_KEY, JWT_SECRET (≥32 chars — the server refuses to boot otherwise)

cd server && npm run dev     # API on :4000 (node --watch)
cd client && npm run dev     # Vite on :5173 — open this; /api/* is proxied to :4000

No Anthropic key? Everything still runs — the AI endpoints return a clear "AI off" message instead.

Production (Render blueprint)

render.yaml defines a single free-tier web service: npm install && npm run build (root script builds the client, installs the server), npm start, health-checked at /api/health. Express finds client/dist and serves it with an SPA fallback for non-/api paths. Secrets (MONGODB_URI, ANTHROPIC_API_KEY, Brevo/Twilio keys) are set in the dashboard; JWT_SECRET is Render-generated.

09 · Field notes

The decisions you'd otherwise rediscover the hard way

  • dns.setDefaultResultOrder('ipv4first') at boot — Render has no IPv6 egress, so preferring AAAA records made outbound TLS (notably SMTP) fail with ENETUNREACH.
  • trust proxy = 1 — exactly one hop (Render's proxy), so rate limiting sees real client IPs without opening IP spoofing via forged X-Forwarded-For chains.
  • JSON limit is 12 MB on purpose: label photos travel as base64 in JSON bodies. The urlencoded parser stays at 16 KB for the tiny server-rendered auth forms.
  • Meals are embedded in Day docs, not a collection — a diary day is always read and written whole, which keeps the client a simple "fetch all days" load.
  • The resolver is the only unit-tested module (server/test/mealResolver.test.js) precisely because it's the only pure one — and the one where a silent wrong answer would corrupt the log.
  • Estimator totals are re-derived from the per-item breakdown (normalizeMeal) since the model pin rejects the temperature param — consistency comes from reconciliation, not greedy decoding.
  • Disabled ≠ deleted. WhatsApp and voice transcription are kept fully wired behind flags/comments (VOICE_DISABLED, commented mounts in index.js) with re-enable instructions inline — the code is the feature-flag documentation.
